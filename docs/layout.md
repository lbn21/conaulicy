# Layout

Every page follows one consistent layout (Jakub's decision, task 125). Read this before any UI change, and keep it up to date when a shared component changes.

## Address subpages: one skeleton

Every `/adres/<id>/<module>` page (`smieci`, `woda`, and later `prad` or any new module) has the same skeleton, in this order:

1. Breadcrumbs: `PlaceBreadcrumbs` (`web/components/place-page.tsx`, built on the shared `Breadcrumbs`, below), rendered by the root layout's `@breadcrumbs` slot before `<main>` (below); everything below is inside it, from `ModuleMain` (`web/components/module-page.tsx`).
2. Caption (place, street) + h1: `SubpageHeading` (`web/components/place-page.tsx`).
3. „Zmień adres”: part of the same heading (GOV.UK "Change" pattern).
4. „Wywozy sprawdziliśmy …” (waste), „Komunikaty o wodzie sprawdziliśmy …” (water), „Ostatnio sprawdziliśmy …” (weather): `CheckedLine` (`web/components/checked-line.tsx`), from the module's `checkedAt` (`web/lib/modules.ts`), its label per module in `web/lib/hub.ts` (`CHECKED`).
5. The calendar block: `CalendarBlock` (`web/components/subpage-parts.tsx`), a primary `govuk-button` link to the module's ICS file, a hint under it (only the page's own sentence on what the file is), then a closed `govuk-details` „Jak dodać i sprawdzić, czy się udało?” with the shared `CALENDAR_STEPS`: how to add it on an iPhone and on Android, what to check and try, and Google Calendar on a computer; a browser never knows whether the import worked, so the copy never says it did. Only the hint comes from the page; the rest, details included, lives only in the component, the same on every page. Its `event` prop and properties are what `web/components/web-analytics.tsx` sends on a click: waste `calendar_add` with `zone` and `source`, water `water_calendar_add` with `place` (the place id). Shown only when the file has at least one event (water: `waterCalendarHref`, `web/lib/water-ics.ts`; waste: a zone with upcoming dates).
6. The module's content (waste: the pickup list; water: the cuts, a day each, then „Inne komunikaty”).
7. The AI-read note: `AiReadNote` (`web/components/subpage-parts.tsx`), GOV.UK's warning text. Wording per source: `UNVERIFIED_NOTE` (`web/lib/schedule-notes.ts`) for the gmina's schedule, `waterAiNote` (`web/lib/water-module.ts`) for the water posts, naming the source of the cuts shown (the gmina's, MZGKiM's or both).
8. The source in an inset: `SourceInset` (`web/components/subpage-parts.tsx`), one „Źródło: …” paragraph per source.

With no calendar file, or nothing to show, the rest keeps the same order. New subpages reuse these shared components instead of re-creating them. `web/components/subpages.test.ts` renders `/smieci` and `/woda` and checks the order and that both calendar blocks have the same markup.

## Breadcrumbs

One component, `Breadcrumbs` (`web/components/breadcrumbs.tsx`), GOV.UK's breadcrumbs: every item a link, the page itself left out, `aria-label` „Ścieżka nawigacyjna”.

- Only on the address pages (`/adres/<id>` and its subpages): „Strona główna”, the locality, and on a module's subpage the address page (`PlaceBreadcrumbs`, `web/components/place-page.tsx`).
- None anywhere else: `/o-projekcie`, `/prywatnosc`, `/dostepnosc`, `/ulice`, the home page and the 404. GOV.UK: „Do not use the breadcrumbs component on websites with a flat structure”, and the rest of the site is flat (Jakub's decision, task 149; task 146 had added „Strona główna” there).
- Before `<main>`, inside `govuk-width-container`, as GOV.UK places them: „Always place breadcrumbs at the top of a page, before the `<main>` element”, so the skip link („Przejdź do treści”, `#main-content`) skips them along with the header. One `<main id="main-content">` for the whole site, the root layout's (`web/app/layout.tsx`; task 227): Next.js keeps a page left by a client-side navigation in the document, hidden (Activity, nextjs.org/docs/app/guides/preserving-ui-state), so a `<main>` per page would repeat the skip link's target, and a layout is never duplicated. Pages render only their content. The breadcrumbs come from the layout's `@breadcrumbs` slot (Next.js parallel routes, nextjs.org/docs/app/api-reference/file-conventions/parallel-routes), rendered right before `<main>`: one slot page per address route (`web/app/@breadcrumbs/adres/…`, each `PlaceCrumbs`, `web/components/place-crumbs.tsx`: nothing for an unknown place or module), `null` for the home page and every other path (`page.tsx`, `[...catchAll]/page.tsx`, so a client-side navigation clears the slot) and `default.tsx` (`null`) on a full load. Why a slot at all: the breadcrumbs come before `<main>`, which is the root layout's, so no page or nested layout can render there. Why one page per address route, not one catch-all that reads the path (tried in task 228): with Partial Prefetching, a link to `/adres/<id>/woda` then prefetched the catch-all's segment without end (12 234 requests in 15 s in CI), never getting it; slot pages shaped like the routes have the same params (`[id]`, `[module]`, `[...nr]`) as the pages, so their prefetch resolves as the pages' does. `check-html` asserts exactly one `<main id="main-content">` in every route's static HTML; `check-a11y` one visible `<main>` and no id twice on four representative routes. The IMGW banner is the first thing in `<main>` on every page that has it (every page but the address pages and the 404 page, `docs/data/imgw.md`).
- Spacing as when they were inside `<main>`: `govuk-!-margin-top-7` stands in for main's top padding, and GOV.UK's own 10 px margin-bottom plus main's padding give the 30/50 px gap to the h1. GOV.UK's spacing scale has no 20/40 px step, so on mobile they sit 5 px lower than before (25 px under the header, not 20); identical from tablet up.

`web/components/breadcrumbs.test.ts` renders the component and the address page's frame; `web/scripts/check-warnings.mjs` checks on every route that they appear only on address pages, right before `<main>`.

## Navigation

Every link to a page of the site is Next.js's `<Link>` (`next/link`, nextjs.org/docs/app/api-reference/components/link; task 228): the header's logo, the breadcrumbs, the footer's links, the home page's examples and its link to `/ulice`, `/ulice`'s list, the hub's links to its subpages, the search's results, „Zmień adres”, the 404's link home, the links between the static pages and a module's own links to an address page (`Parts`, `web/components/parts.tsx`, by an href starting with `/`). A click is a client-side navigation: one document, the layout (header, footer, `<main>`) kept, only the page and the breadcrumbs slot replaced. A plain `<a>` stays for another site, a file (the ICS and PDF links, `webcal:`, `/fonts/OFL.txt`), `mailto:` and an anchor on the same page (the hub's „Szczegóły i źródło”, the error summary's link to its field, the skip link).

- **Prefetch:** Next.js's default for every link, except links to an address page in a small list, which prefetch in full (task 238, Jakub's decision, 1 Nov 2026), below. With Partial Prefetching (`next.config.ts`) a link prefetches its route's App Shell, one per route, shared by every link to it, so `/ulice`'s list of links to one route prefetches one shell, not one per link (nextjs.org/docs/app/guides/prefetching, "Partial Prefetching"). The address pages and their breadcrumbs read the place (`params`) behind `<Suspense>` (`PlaceSuspense`, `web/components/place-suspense.tsx`; nextjs.org/docs/app/guides/adopting-partial-prefetching#move-url-data-behind-suspense), so their shell holds the layout and the place's skeleton (its first screen's shape) and its prefetch finishes; after a click the place streams in. A prerendered place's full load has its h1 and breadcrumbs in the static HTML, after the skeleton (React's hidden `<div>`, swapped in by its inline script), not in place: accepted (Jakub's decision, task 231; tried and reverted in task 228 for that reason). Before, links to an address page were not prefetched (`prefetch={false}`, task 228), and a per-link `prefetch={true}` with the place read outside `<Suspense>` never let the home page reach network idle (task 231). `ensureStatic = "prefetch"` on the root layout keeps every prefetch static output, never a server render (nextjs.org/docs/app/api-reference/file-conventions/route-segment-config/ensureStatic). Costs: `docs/perf.md`.
- **Full prefetch for street links (task 238):** with the default, a click on a place fetches its own static content only after the click (about 420 ms, the skeleton shown about 0.35 s); `prefetch={true}` fetches it with the App Shell (nextjs.org/docs/app/api-reference/components/link#prefetch: „With Partial Prefetching enabled, the prefetch includes the App Shell and cached content that depends on the link's URL data”), so the place's h1 is there when the navigation commits (measured on production, 16.4.2: 75–124 ms, no skeleton; about 3 static requests, 9 KB, per link). The rule:
  - **Small lists: full.** The home page's sample addresses, the search's results, the address pages' links to their subpages, their breadcrumbs, and a module's link to another place (a water cut's locality page): `prefetch={addressPrefetch(href)}` (`web/lib/address-routes.ts`).
  - **`/ulice` (336 links): on intent.** `PlaceLink` (`web/components/place-link.tsx`) prefetches as the default until a pointer enters the link, it gets focus or a touch starts, then in full: `prefetch={active ? true : 'auto'}`, as the docs ask for many visible links (nextjs.org/docs/app/guides/optimizing-prefetching; nextjs.org/docs/app/guides/prefetching#hover-triggered-prefetch). The same `<a>`, server-rendered; nothing visible changes. Its chunk is the only JS `/ulice` loads beyond a static page's (`check-all-places`: one chunk, at most 1 KB gzip); it does not import `addressPrefetch`, as its href is always `placePath(id)`.
  - **Never to a redirect source.** `addressPrefetch` gives `true` only for a canonical `/adres/<id>` or `/adres/<id>/<module>`, which is prerendered: no query (a `?nr=` is rewritten to a number page rendered on its first visit), no trailing slash, no `/nr/…` (`numberRedirects`) and no file; anything else gets the default (`web/lib/address-routes.test.ts`). The ids come from the same cached dataset as the pages, so a renamed place's old id (`proxy.ts`'s 308) is never linked; a search index loaded before an import may still hold one until the page is reloaded (that link then meets the 308; not measured).
  - `router.prefetch(…, { kind })` is undocumented, so never used (below); no `staleTimes` or other config for it.
- **Live blocks stay fresh:** a link's navigation always fetches the page itself (Next.js caches no page in the browser, only reuses one on Back and Forward: nextjs.org/docs/app/glossary#client-cache and nextjs.org/docs/app/api-reference/config/next-config-js/staleTimes, `dynamic` 0 s), so each `<Suspense>` hole is read again, as on a full load. Back and Forward show the page as it was left, its blocks as they were then, as the browser's own back/forward cache does after a full load.
- **Focus and scroll:** Next.js's route announcer (a polite region) says the new page's title (`document.title`, nextjs.org/docs/architecture/accessibility, "Route Announcements"); focus stays where it was, as Next.js leaves it: on the header's or footer's link, which stays, or on the body when the clicked link left with its page (the skip link is then the next Tab). The page scrolls to its top when its start is out of view (`<Link>`'s `scroll`, default, nextjs.org/docs/app/api-reference/components/link#scroll). No own focus code.
- **State left on a page:** Next.js keeps up to 3 pages left by a navigation in the document, hidden (Activity, nextjs.org/docs/app/guides/preserving-ui-state; react.dev/reference/react/Activity), by design: two hubs visited in turn are both there, so their ids (`woda`, `woda-heading`, …) are there twice while both are kept (accepted, Jakub's decision, task 228); the checks look for an id twice within one page. The home page's search starts over on every visit by a link („Zmień adres”, the logo), as CLAUDE.md asks, and comes back as it was on Back: its column is keyed by `useRouter().bfcacheId` (`SearchErrorProvider`, `web/components/address-search.tsx`; nextjs.org/docs/app/api-reference/functions/use-router#bfcacheid). GOV.UK Frontend's JavaScript starts the components of each new page (`web/components/govuk-frontend.tsx`, on each new path).
- **The search's one place:** „Szukaj” opens it with `useRouter().push` (task 227); the place's page comes with the navigation, its h1 streamed after the address route's App Shell (above); `router.prefetch` fetches only the App Shell in Next.js 16.4 (its `kind` option is undocumented, and `FULL` is the legacy full prefetch that also renders the live blocks), so it is not used.

Leśna, Lubaczów – conaulicy.pl”, a village's street „ul. Leśna, Basznia Dolna – conaulicy.pl”, a whole village „Antoniki, gm. Lubaczów – conaulicy.pl”; `/smieci` „Odbiór śmieci: wszystkie terminy – ul. Leśna, Lubaczów – conaulicy.pl”, `/woda` „Przerwy w dostawie wody – ul. Leśna, Lubaczów – conaulicy.pl”. Built from the place's label (`titleLabel`, `web/lib/places.ts`); `web/scripts/check-metadata.mjs` checks the pattern, `check-indexing.mjs` that no two titles in the sitemap are the same.

## Headings

- One h1 per page.
- Module and section headings are h2 (on the hub `govuk-heading-l`, on other pages `govuk-heading-m`); no skipped levels.
- When a list needs a section heading for screen readers but not on screen, it gets a visually hidden h2 (`govuk-visually-hidden`), as the pickup list on `/smieci` (`web/components/pickup-schedule.tsx`).

## Indexing

- Indexed, and in the sitemap (`web/app/sitemap.ts`): the static pages, and for each place with data its hub and `/smieci`.
- `noindex` and not in the sitemap: `/woda` (its content lasts days and is mostly empty; it stays so), the house-number variants (`?nr=`, `/nr/…`, canonical to the hub), `/numer`, PDFs, ICS files, and places with no data.
- `web/scripts/check-indexing.mjs` checks both lists, and that every URL in the sitemap is indexable (200, no noindex, canonical itself).

## Site-wide: the same job, the same component

Across the whole site the same job always uses the same component and style:

- one button style per action (adding to a calendar: the primary `govuk-button`, `CalendarBlock`);
- one place for what is coming soon (the hub's „Najbliższe dni”, `Upcoming` in `web/components/upcoming.tsx`): a line per item, „Szczegóły i źródło” to its section's anchor, where its source and check time are (task 207);
- one freshness line: `CheckedLine` on the subpages; on the hub, the end of each section's meta line („Sprawdziliśmy …”, `metaLine`, `web/lib/hub.ts`).
- Link text says where it goes (e.g. „Wszystkie odbiory śmieci”); never a bare „Szczegóły” or „Kliknij tutaj”.

## Live blocks and loading placeholders

Every page is a static shell; what changes between imports is a live block, its own `<Suspense>` hole read per request (`LiveBlock`, `web/components/live-block.tsx`; Jakub's decision, 31 Oct 2026): the IMGW line or banner on every page but the address pages, and on the address pages „Najbliższe dni” and each live module's section body (water, weather; power later, by the module's `live` flag), and `/woda`'s body under its heading. One rule for every block (tasks 235 and 237): **a fallback reserves the first screen's final height, below it kept simple; empty states are plain text; skeletons are seen as soon as they render.**

- **Skeleton:** its typical shape, reserved (`Skeleton`, `web/components/skeleton.tsx`): blank space as wide as the typical text, in the element and GOV.UK class it will have, on GOV.UK's light grey (`.app-skeleton`), line for line, so it scales with text zoom. Blank, so no crawler or text-only reader finds words in it. The typical shape: the IMGW quiet line; a section's status line (a live module's `typical`, its own words for nothing planned: `NO_CUTS`, `NO_WARNINGS`), its link and its meta line; „Najbliższe dni”'s heading, its empty state's one line and its break (the usual state, 20 of 24 addresses on 1 Nov 2026; a pickup tomorrow is 25 px taller on a phone, 50 px on a desktop; never gone: below). A shape's pieces sit in the same wrappers as the page's (a `<div>` for a `<section>`), as GOV.UK pads a heading right after a `govuk-body` (`.govuk-body + .govuk-heading-m`). The address pages' params are behind `<Suspense>` too (`PlaceSuspense`, `web/components/place-suspense.tsx`): its fallback is the page's typical first screen, from the same pieces (`HUB_SHAPE` in `web/components/hub.tsx`, `LIVE_SHAPE` in `web/components/module-page.tsx`), matched at 390×844 and 1280×800 (task 237): the h1's line, „Zmień adres”, then on the hub „Najbliższe dni”, every section's heading and body (the waste section's bins one row), the breaks and IMGW's wording; on a live subpage its caption and the water's lines; on the waste subpage its caption, checked line, the calendar's button (GOV.UK's button box, `govuk-button` on a span), hint and details, the PDF link, the next pickup's big date and its first bins (`BinsSkeleton`, `web/components/waste-bins.tsx`); one „Sprawdzamy…” for all of it. Below the first screen it stays simple: every address's page is as long as its own content. The waste subpage has its own route folder (`web/app/adres/[id]/smieci/`, a static segment wins over `[module]`) so that its fallback is its own, as the module is in the params; every subpage route shares one body (`SubpageRoute`, `web/components/subpage-route.tsx`). The breadcrumbs' slot has its own fallback, the trail's one line, on a subpage with the address (`CrumbsRoute`, `web/components/place-crumbs.tsx`, one for every address route; a long name wraps the trail to two lines on a phone, 11 of 28 waste subpages). More or less content shifts what follows a little on reveal (accepted; the checks hold it to web.dev's "good" CLS, 0.1).
- **Motion:** a skeleton is seen as soon as it renders, no delay and no fade in (task 237: the 300 ms delay of task 235 showed a blank page between the click and the content); CSS only, on `.app-skeleton` (a shape's section break and button take the class too; no shadow and no pointer, so GOV.UK's button `:hover` never recolours it); a subtle pulse (opacity only); the reveal through React's `<ViewTransition>` as Next.js's "Suspense reveals": the skeleton fades out and the block fades in, opacity only, 150 ms each, at once, no slide; the page itself never crossfades (`::view-transition-*(root)` off), so a reload while scrolled does not jump and a navigation swaps at once (`web/app/site.scss`, task 233). The IMGW row is at least one `govuk-body-s` line tall (`.app-imgw` on its `govuk-grid-row`), skeleton and quiet line alike. The main content takes no scroll anchor (`overflow-anchor: none` on `#main-content`, task 234), so a reload restores the plain scroll offset, not Chromium's saved anchor, which at first layout, skeletons still in place, matched the wrong box and landed the page too high. Under `prefers-reduced-motion: reduce` no pulse and no reveal: the skeleton is still, and the block swaps at once. `::view-transition { pointer-events: none }`, so clicks during a reveal reach the page.
- **Screen readers:** the skeleton is `aria-hidden`; once per placeholder, „Sprawdzamy…” in `govuk-visually-hidden` (`LOADING`). No live region and no `aria-busy`: nothing is announced on load, and the fallback is replaced, not updated in place, so there is no element left to mark busy.
- **Freshness:** a block's „Sprawdziliśmy” comes from the same read as its data. The IMGW line is always there: „Ostrzeżenia IMGW: brak ostrzeżeń dla powiatu lubaczowskiego · sprawdziliśmy 14:52” when there is none, its source linked.
- **„Dziś”, „Jutro”, „Za 5 dni”:** the device's, never the server's (`DayWord`, `web/components/day-word.tsx`, `use(browser())`): a word-wide skeleton in the HTML, then the word. The dates around it are absolute, with their weekday, in the HTML.

The search lives only on the home page (no `/szukaj`, task 227): its field is in the static shell, the same element before and after hydration (`web/components/address-search.tsx`). What „Szukaj” finds is drawn under the field, in a polite live region: one place opens its page; several are listed („Wyniki wyszukiwania”, h2, then „Dla „…” znaleźliśmy 3 adresy. Wybierz swój.” and the links); none is plain text, never an error („Nie znaleźliśmy „…””, h2, then what to try). While the index is still loading, `web/components/search-skeleton.tsx` (one result) holds the place. GOV.UK's error summary and field error only for an empty submit, never on load.

## Home-screen app

Opened from the home screen (`display-mode: standalone`), every page has a strip in the header's colour, 10 px deep, fixed at the top (`.govuk-template__body::before`, `web/app/site.scss`; task 136): Safari 26 takes the status bar's colour from it, not from theme-color. ## The hub, `/adres/<id>`

The hub keeps its own layout (`web/components/hub.tsx`): „Najbliższe dni” under „Zmień adres”, always, then one section per module, always, in registry order: Śmieci, Woda, Pogoda (`MODULE_IDS`, `web/lib/address-routes.ts`; task 207), each with its module's id as its anchor (`<section id="woda">`). Each section's heading is in the cached shell; a live module's body is its own live block (above), which says „Jeszcze tego nie sprawdziliśmy.” while its source has no file yet (an old copy shows a notice instead, `docs/data/imgw.md`).

„Najbliższe dni” (`web/components/upcoming.tsx`, a client island; its rules in `web/lib/upcoming.ts`): h2 `govuk-heading-m`, then a `govuk-list govuk-list--spaced`, then a visible `govuk-section-break--l`. Each module gives structured items (`Module.upcoming`): water cuts and IMGW warnings while announced and not over (no end: until the end of its day), pickups only today and tomorrow, „Wystaw je …” only before its time. One order: start, then end, then `MODULE_IDS`; no priority by module or level. Each item: the lead word in `<strong>` („Teraz”, „Dziś”, „Jutro” or its date) and the sentence (IMGW's level as its tag); its second sentence on its own line (where, from structured fields only, never the source's `note`; or when to put the bins out). A whole locality is „wieś” or „miejscowość” by its TERYT kind (`placeWord`, `web/lib/water-module.ts`), the same word as the Woda section's „Gdzie”; a failure reads „(awaria)” after what happens, whatever the lead; then „Szczegóły i źródło” with a visually hidden „: woda / pogoda / odbiór śmieci”, to the section's anchor, where the source and check time are. Nothing shown: the heading, then one plain `govuk-body` line, „W najbliższych dniach nic się u Ciebie nie dzieje.” (`NOTHING_SOON`), then the break, so the block never leaves its place (task 235). The island hydrates with the server's render time, then follows the device's clock (every minute and when the tab comes back), keeping the server's words when the clock is over 5 minutes before the render; all labels are made on the server, all comparisons are Warsaw days and instants.

Each section, in this order:

1. h2 `govuk-heading-l`, the module's title.
2. Its status (`Module.status`, `web/lib/modules.ts`): groups of lines, never empty. Each line a `govuk-body` paragraph (a row of bins: a `div`); lines of a group close under each other (`govuk-!-margin-bottom-2`), the group's last keeps the paragraph's gap. Dates absolute in the HTML („środa, 4 listopada”); a section's first date line gets its lead from the same island (`DayLead`): „Dziś: ”, „Jutro: ”, „Za N dni: ” for 2 to 7 days, beyond that the date alone, capitalised. A label with a colon („Gdzie: …”, „Kolejne dni: …”) ends without a full stop, as its value may end in the source's own words.
   - Śmieci: the next pickup's day; „Tego dnia odbiorą:”, or „Tego dnia odbiorą wszystkie pojemniki:” when that day has every fraction the zone has (all its events, past ones too; more than one); its bins in a row (`Bins` size `small`: 14×20 marks, GOV.UK's `govuk-!-display-inline-block` and `govuk-!-margin-right-3` / `-1`, no own CSS); „Wystaw je do 6:00 rano.” when the data has a time (`putOutLine`, `web/lib/schedule-notes.ts`).
