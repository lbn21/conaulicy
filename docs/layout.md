# Layout

Every page follows one consistent layout. Read this before any UI change, and keep it up to date when a shared component changes.

## Every page: one skeleton, one visual layer

Every page, whatever its route (home, the hub, each subpage, `/ulice`, the static pages, the 404), is the same three sections:

1. **The page head** (`PageHead`, `web/components/page-head.tsx`): a band in the brand's surface tint (`surface-background`, wiśnia tint-95), the full width of the window, straight under the header (or the address pages' breadcrumbs). It holds, in this order, only what comes before the content: the error summary, the caption, the h1 (on a module's subpage with the module's icon on its tile), a lead (`govuk-body-l`) and the page's first action („Zmień adres”; on the home page the search itself, no card around it). `.app-band` in `web/app/site.scss`: full width by a clipped 100vmax shadow (nothing overflows), pulled up over `<main>`'s top padding; its last line's margin is the band's padding.
2. **The content**, on white, in GOV.UK's two-thirds column, built only from shared parts:
   - **Module colours and icons:** each module has a colour (`MODULE_COLOURS`, `web/lib/palette.ts`; [brand](brand.md#module-colours)) and a Lucide icon (`Icon`, `Tile`, `web/components/icon.tsx`: waste Trash2, water Droplet, power Zap, weather CloudSun; Clock for hours, TriangleAlert for failures and warnings, ChevronRight, MapPin, CalendarDays, FileText). `.app-mod--<id>` sets the module's colours as custom properties for everything inside it; a subpage's whole body is in its module's. Icons are drawn on the server from the framework-free `lucide` package (no client JS), always `aria-hidden` and always beside words that say the same.
   - **Badges** (`Badge`, `web/components/badge.tsx`, `.app-badge`): a pill of 16 px bold text: muted (grey: „Odwołane”), the module's (its tint and ink: „Planowana”, „Planowane wyłączenie”, a count), alert (GOV.UK red with the warning icon: „Awaria”), strong (text colour: „Dzisiaj”, „Jutro”). Words always; colour never alone. Only when there is something to show: an empty state is never a badge.
   - **Chips** (`.app-chips`, `.app-chip`): a wrapping row of bordered pills: each window of hours its own (`TimeChips`, `web/components/rows/outage.tsx`, with the clock), the small bins, the home page's example addresses (links, the whole chip the target).
   - **Cards** (`.app-card`, shadcn/ui's Card): white, a subtle border and shadow, rounded; a summary list inside keeps GOV.UK's row borders but the last. `--accent`: a bar in the module's colour (`/smieci`'s next pickup). The timeline's day cards are the same look (`.app-timeline__card`).
   - **Item cards** (`.app-items`, `.app-item`, shadcn/ui's Item): a tile, the body, a chevron; the link's box the whole card's. `--plain`: tile and text only (the home page's „Co zobaczysz”).
   - **Empty states** (`.app-empty`): plain text in GOV.UK's secondary text colour, regular weight, no frame, pill, background or colour: „Na razie nic nie zaplanowano…”, a subpage with nothing to show, „Nie udało się sprawdzić…”, no waste dates.
   - **The failure banner** (`NowBanner`, `web/components/now-banner.tsx`, `.app-alert`): at the top of the hub's content, only while a failure is on at the address at the read (an outage marked emergency whose span holds the instant): GOV.UK red, „Teraz trwa awaria”, each cut with its hours as chips and „Szczegóły”. Read with the page; nothing appears later on its own. IMGW's warnings stay the cards above the timeline.
3. **The footer's band** (`web/components/site-footer.tsx`), unchanged.

Red is only for what is urgent (a failure, IMGW's level 3); a module's colour never is. Today and tomorrow stand out (the strong badge, a dark ring round the day's card, its dot filled); quieter things are quieter (an empty day is grey text, no card). No toasts, popups, or anything that appears or moves on its own; CSS only, no JS for looks.

## Address subpages: one skeleton

Every `/adres/<id>/<module>` page (`smieci`, `woda`, `prad`, and any new module; the weather has none) has the same skeleton, in this order, from one frame: `Subpage` (`web/components/module-page.tsx`, built on `AddressPage`, `web/components/place-page.tsx`), filled only from the module's fields (`Module`, `web/lib/modules.ts`); the module's `Details` is the body alone, from step 5:

1. Breadcrumbs: `PlaceBreadcrumbs` (`web/components/place-page.tsx`, built on the shared `Breadcrumbs`, below), rendered by the root layout's `@breadcrumbs` slot before `<main>`; everything below is inside it, from `ModuleMain` (`web/components/module-page.tsx`).
2. The page head's band (`PageHead`, above): caption (place, street) + h1 (`Module.pageTitle`, the module's icon on its tile before it); before them, GOV.UK's error summary when the module has an error (`Module.error`: waste's house-number question).
3. „Zmień adres”: the band's last line (GOV.UK "Change" pattern).
4. The calendar block: `CalendarBlock` (`web/components/subpage-parts.tsx`), a primary `govuk-button` link to the module's ICS file (the calendar icon before its words), a hint under it (only the page's own sentence on what the file is), then a closed `govuk-details` „Jak dodać i sprawdzić, czy się udało?” with the shared `CALENDAR_STEPS`: how to add it on an iPhone and on Android, what to check and try, and Google Calendar on a computer; a browser never knows whether the import worked, so the copy never says it did. Only the hint comes from the page; the rest lives only in the component, the same on every page. Its `event` prop and properties are what `web/components/web-analytics.tsx` sends on a click: waste `calendar_add` with `zone` and `source`, water `water_calendar_add` with `place` (the place id). Shown only when the file has at least one event (water: `waterCalendarHref`, `web/lib/water-ics.ts`; waste: a zone with upcoming dates).
5. The module's content (waste: the next pickup in an accent card, the next two dates in a card, the rest under „Pokaż więcej terminów”; outages, water and power alike: a day each, a card per outage with its summary list, each window of hours a chip, „od 8:00 do 14:00” (`fromTo`, `hoursRow` in `web/lib/outage-view.ts`), a value longer than 160 characters (PGE's house numbers) folded into a `govuk-details` „Pokaż całą listę”, then „Inne komunikaty”; nothing to show: the empty state). Water and power share one body (`OutageDetails`, `web/components/outage-page.tsx`), drawn from one shape (`OutagePage`, `web/lib/outage-view.ts`) that each fills from its own data (`waterPage`, `web/components/water-page.tsx`; `powerPage`, `web/lib/power-module.ts`): water's rows are „Godziny” and „Gdzie”; power's „Godziny”, „Rodzaj” (a badge: „Awaria” alert, „Planowane wyłączenie” the module's; revoked, a muted „Odwołane” and the kind in words with PGE's note), „Gdzie” (TERYT names) and „Numery domów według PGE” (verbatim). Power has no calendar, AI note or other notices.
6. The AI-read note: `AiReadNote` (`web/components/subpage-parts.tsx`), GOV.UK's warning text. Wording per source: `UNVERIFIED_NOTE` (`web/lib/schedule-notes.ts`) for the gmina's schedule, `waterAiNote` (`web/lib/water-module.ts`) for the water posts, naming the source of the cuts shown (the gmina's, MZGKiM's or both).
7. The page's one source block, at the bottom, in an inset: `SourceInset` (`web/components/subpage-parts.tsx`), one paragraph „Źródło: ‹`Module.sources`, joined with ;›. Sprawdziliśmy 10 listopada 22:40.” (`sourceLine`, `web/lib/hub.ts`, from the module's `checkedAt`; one `Intl.DateTimeFormat`, or the day alone), each part only when there is one; `/woda` with no cut names the news pages. No checked line under „Zmień adres”.

With no calendar file, or nothing to show, the rest keeps the same order. A module with no data (`load` → null) shows steps 1–3, then the hub's one line, „Nie udało się sprawdzić ‹`Module.subject`›.” (`unchecked`, `web/lib/hub.ts`), as the empty state (`app-empty govuk-body`). New subpages reuse these shared components instead of re-creating them. `web/components/subpages.test.ts` renders `/smieci` and `/woda` through `Subpage`, checks their order, the no-data state, and that both calendar blocks have the same markup.

Metadata, one builder for every module (`moduleMetadata`, `web/components/subpage-route.tsx`): the title „‹h1› – ‹place›” („Błąd: ” first on `Module.error`), `Module.description`, and `noindex` unless `Module.indexed` says it may be a search result (waste only, as the address page: `indexedPlace`).

## Breadcrumbs

One component, `Breadcrumbs` (`web/components/breadcrumbs.tsx`), GOV.UK's breadcrumbs: every item a link, the page itself left out, `aria-label` „Ścieżka nawigacyjna”.

- Only on the address pages (`/adres/<id>` and its subpages): „Strona główna”, the locality, and on a module's subpage the address page (`PlaceBreadcrumbs`, `web/components/place-page.tsx`). Collapsed on mobile (`govuk-breadcrumbs--collapse-on-mobile`: below tablet only the first and last crumb, on one line), so a chevron never starts a line on its own.
- None anywhere else: `/o-projekcie`, `/prywatnosc`, `/dostepnosc`, `/ulice`, the home page and the 404. GOV.UK: „Do not use the breadcrumbs component on websites with a flat structure”, and the rest of the site is flat.
- Before `<main>`, inside `govuk-width-container`, as GOV.UK places them („Always place breadcrumbs at the top of a page, before the `<main>` element”), so the skip link („Przejdź do treści”, `#main-content`) skips them along with the header.
- One `<main id="main-content">` for the whole site, the root layout's (`web/app/layout.tsx`): Next.js keeps a page left by a client-side navigation in the document, hidden (Activity), so a `<main>` per page would repeat the skip link's target; a layout is never duplicated. Pages render only their content.
- The breadcrumbs come from the layout's `@breadcrumbs` slot (Next.js parallel routes), rendered right before `<main>`, since no page or nested layout can render there: one slot page per address route (`web/app/@breadcrumbs/adres/…`, each `PlaceCrumbs`, `web/components/place-crumbs.tsx`: nothing for an unknown place or module), `null` for the home page and every other path (`page.tsx`, `[...catchAll]/page.tsx`, so a client-side navigation clears the slot) and `default.tsx` (`null`) on a full load. The slot pages are shaped like the routes, with the same params (`[id]`, `[module]`, `[...nr]`), so their prefetch resolves as the pages' does; a single catch-all slot that reads the path never finishes its prefetch under Partial Prefetching.
- `check-html` asserts exactly one `<main id="main-content">` in every route's static HTML; `check-a11y` one visible `<main>` and no id twice on four representative routes.
- Spacing: one token above and below the trail, `govuk-!-margin-top-7` and `govuk-!-margin-bottom-7` (25 px on mobile, 40 px from tablet), so the gap from the header to the trail equals the gap from the trail to the page head's band. The margin-top stands in for main's top padding; below, the band cancels main's padding (`.app-band`), so the margin-bottom alone is the gap. `breadcrumbs.test.ts` checks both use the same step.

`web/components/breadcrumbs.test.ts` renders the component and the address page's frame; `web/scripts/check-warnings.mjs` checks on every route that they appear only on address pages, right before `<main>`.

## Navigation

Every link to a page of the site is Next.js's `<Link>` (`next/link`): the header's logo, the breadcrumbs, the footer's links, the home page's examples and its link to `/ulice`, `/ulice`'s list, the hub's links to its subpages, the search's results, „Zmień adres”, the 404's link home, the links between the static pages and a module's own links to an address page (`Parts`, `web/components/parts.tsx`, by an href starting with `/`). A click is a client-side navigation: one document, the layout (header, footer, `<main>`) kept, only the page and the breadcrumbs slot replaced.

A link to an id on the same page is a `<Link>` too, `FragmentLink` (`web/components/fragment-link.tsx`, no prefetch): the error summaries' links to their field and the skip link. A plain `<a href="#…">` makes a history entry the App Router does not know, so Back would show another page under the current URL; a `<Link>` pushes its own entry and scrolls to the id. GOV.UK's scripts keep their part: the error summary's focuses its field (and stops the navigation), the skip link's focuses `<main>`.

A plain `<a>` stays only for another site, `mailto:` and a file the browser opens itself (the ICS and PDF links, `webcal:`, `/fonts/OFL.txt`); `web/components/internal-links.test.ts` holds every plain `<a>` to that, and the routes check `in-page` (`web/scripts/routes/in-page.mjs`) clicks the skip link, then the logo, then Back, and opens `#skad-to-wiemy` directly.

- **Prefetch:** Next.js's default for every link, except links to an address page (below). With Partial Prefetching (`next.config.ts`) a link prefetches its route's App Shell, one per route, shared by every link to it, so `/ulice`'s list prefetches one shell, not one per link. The address pages and their breadcrumbs read the place (`params`) behind `<Suspense>` (`PlaceSuspense`, `web/components/place-suspense.tsx`), so their shell holds the layout and the skeleton and its prefetch finishes; after a click the page streams in, whole. A house number is `?nr=`, read from `searchParams` behind the same boundary after `navigation()` (`numberQuery`, `web/components/place-page.tsx`), so the shell and the per-link prefetch stay static; `generateMetadata` reads it too, so an address page's title, canonical and robots stream with the page: at the end of `<body>` for a browser, in `<head>` for Next.js's HTML-limited bots. A place's static HTML holds only the skeleton. `ensureStatic = "prefetch"` on the root layout keeps every prefetch static output, never a server render. Costs: `docs/perf.md`.
- **Full prefetch on intent, for every link to an address page:**
  - **On intent, everywhere.** Every link to an address page is `PlaceLink` (`web/components/place-link.tsx`): `/ulice`'s list, the home page's sample addresses, the search's results, the address pages' links to their subpages, the breadcrumbs, and a module's link to another place (a water cut's locality page). It prefetches as the default until a pointer enters the link, it gets focus or a touch starts, then in full: `prefetch={active ? addressPrefetch(href) : 'auto'}`, as Next.js's guide for hover-triggered prefetch with Partial Prefetching. The same `<a>`, server-rendered; nothing visible changes.
  - **Never `prefetch={true}` on first render:** eager on the home page's sample addresses, `/` never reaches network idle.
  - **Never to a redirect source.** `addressPrefetch` (`web/lib/address-prefetch.ts`) gives `true` only for a canonical `/adres/<id>` or `/adres/<id>/<module>`, which is prerendered: no query (a `?nr=` is read from `searchParams`, so its per-link prefetch would be rendered per request), no trailing slash and no file; anything else keeps the default (`web/lib/address-routes.test.ts`). The ids come from the same cached dataset as the pages, so a renamed place's old id (`proxy.ts`'s 308) is never linked; a search index loaded before an import may still hold one until the page is reloaded.
  - **Small:** `addressPrefetch` imports only `web/lib/module-ids.ts`, so `PlaceLink`'s chunk is tiny; it is the only JS `/ulice` loads beyond a static page's (`scripts/routes/all-places.mjs`: one chunk, at most 1 KB gzip).
  - `router.prefetch(…, { kind })` is undocumented, so never used; no `staleTimes` or other config for it.
- **Unknown addresses are a 404 from the first answer.** An address route sends its prerendered shell, a 200, before the page knows the place, so the page's own `notFound()` cannot set the status. `proxy.ts` therefore answers the 404 page itself, before any render: for anything after an id that is no subpage or file, and for an id that is neither a place nor a renamed one (`unknownAddress`, `web/lib/address-routes.ts`; the ids come from `/api/places`, held in memory for 5 minutes; an id the list lacks reloads it first, at most once a second, so a place an import has just added works at once). If that list cannot be loaded, an unknown id falls back to the page's `notFound()`. The 404 is the proxy's own response (the `/404` page's HTML, fetched once per instance, with status 404), never a rewrite to `/404`: Vercel serves such a rewrite with the stored `/404` result's 200, though a local `next start` sends 404. `web/proxy.test.ts` therefore checks the proxy's own status; `check-routes` (`query`), `check-indexing` and `check-html` require the 404 on the first request.
- **Live blocks stay fresh:** a link's navigation always fetches the page itself (Next.js caches no page in the browser, only reuses one on Back and Forward; `staleTimes.dynamic` 0 s), so each `<Suspense>` hole is read again, as on a full load. Back and Forward show the page as it was left, as the browser's back/forward cache does after a full load.
- **Focus and scroll:** Next.js's route announcer (a polite region) says the new page's title; focus stays where it was, as Next.js leaves it: on the header's or footer's link, which stays, or on the body when the clicked link left with its page (the skip link is then the next Tab). The page scrolls to its top when its start is out of view (`<Link>`'s default `scroll`). No own focus code.
- **State left on a page:** Next.js keeps up to 3 pages left by a navigation in the document, hidden (Activity), by design: two hubs visited in turn are both there, so their ids are there twice while both are kept (accepted); the checks look for an id twice within one page. The home page's search starts over on every visit by a link („Zmień adres”, the logo) and comes back as it was on Back: its column is keyed by `useRouter().bfcacheId` (`SearchErrorProvider`, `web/components/address-search.tsx`). GOV.UK Frontend's JavaScript starts the components of each new page (`web/components/govuk-frontend.tsx`, on each new path).
- **The search's one place:** „Szukaj” opens it with `useRouter().push`; the place's page comes with the navigation, its h1 streamed after the address route's App Shell. `router.prefetch` fetches only the App Shell, so it is not used.

A place's pages add its locality to the title only, never to the h1, so that search results for the same street name in two places differ: the hub „ul. Leśna, Lubaczów – conaulicy.pl”, a village's street „ul. Leśna, Basznia Dolna – conaulicy.pl”, a whole village „Antoniki, gm. Lubaczów – conaulicy.pl”; `/smieci` „Odbiór śmieci – ul. Leśna, Lubaczów – conaulicy.pl”, `/woda` „Przerwy w dostawie wody – ul. Leśna, Lubaczów – conaulicy.pl”. Built from the place's label (`titleLabel`, `web/lib/places.ts`); `web/scripts/routes/metadata.mjs` checks the pattern, `check-indexing.mjs --expect=index` (by hand) that no two titles in the sitemap are the same.

## Headings

- One h1 per page.
- Module and section headings are h2 (on the hub `govuk-heading-l`, on other pages `govuk-heading-m`); no skipped levels.
- When a list needs a section heading for screen readers but not on screen, it gets a visually hidden h2 (`govuk-visually-hidden`), as the pickup list on `/smieci` (`web/components/pickup-schedule.tsx`).

## Typography

One rule: **19 px for content, 16 px for metadata and chrome, bold only for headings and keys.** Only GOV.UK Frontend v6's type scale and classes, no new sizes or weights (`19` is 19/25 at every width, `16` 16/20, `24` 21→24, `36` 27→36, `48` 32→48, `80` 53→80).

|---|---|---|
| h1 on the home page | `govuk-heading-xl` | 48 (32 on a phone), bold |
| h1 everywhere else, the 404 included | `govuk-heading-l` | 36 (27), bold |
| Caption over a subpage's h1 | `govuk-caption-l` | 24 (21), regular, secondary |
| Lead paragraph (home, static pages, `/ulice`) | `govuk-body-l` | 24 (21), regular |
| Section h2 | `govuk-heading-m` | 24 (21), bold |
| Sub-section and card title, h3 | `govuk-heading-s` | 19, bold |

- The hub's notice inset (`Status`, `web/components/parts.tsx`) is 19: it is content („Nie mamy jeszcze harmonogramu wywozu śmieci dla tej wsi…”, „Nie udało się sprawdzić…”), not metadata.

- `/woda`'s day sections are `govuk-heading-m`, GOV.UK's own size; so is a hub warning card's event (h2, as a section's), its band „Stopień N z 3” `govuk-body-s` bold.

## Indexing

- Indexed, and in the sitemap (`web/app/sitemap.ts`): the static pages, and for each place with data its hub and `/smieci`.
- `noindex` and not in the sitemap: `/woda` and `/prad` (their content lasts days and is mostly empty), a house number (`?nr=`, canonical to the hub), the number error (an empty `?nr=`), PDFs, ICS files, and places without a waste schedule.
- `web/scripts/check-indexing.mjs` checks both lists, and with `--expect=index` (by hand, `docs/launch.md`) that every URL in the sitemap is indexable (200, no noindex, canonical itself).

## Checks and tests: structure, not copy

The route, HTML, PDF and IMGW checks (`web/scripts/**`) and the rendered-markup tests (`web/components/*.test.ts`) check structure and data, never the page's words: an h1 with text, a description, the title's pattern („‹h1› – conaulicy.pl”, a place's with its locality), the order of the page's parts by their markup, dates and times from the data. No check bans a word. A test that needs a page's words reads them from their source (`MODULES`, `unchecked`, `IMGW_ATTRIBUTION`…), so changing copy never breaks a test. The library tests (`web/lib/*.test.ts`) still check which message a state gives, as the behaviour under test.

## Site-wide: the same job, the same component

Across the whole site the same job always uses the same component and style:

- one button style per action (adding to a calendar: the primary `govuk-button`, `CalendarBlock`);
- one place for what is coming soon (the hub's timeline, `Timeline` in `web/components/timeline.tsx`): a card per day, a row per item with „Szczegóły” to its subpage (IMGW's warnings are the cards above it); each module's source and check time on its subpage;
- one freshness line: on a subpage, the end of its source block (`sourceLine`, step 7 above); on the hub, the small print's first sentence, every module with a known check in one list („Sprawdziliśmy: śmieci 10 listopada 22:40, woda 11 listopada 7:00, prąd 11 listopada 7:07 i pogoda 11 listopada 7:07.”, `freshnessLine`, `web/lib/hub.ts`, `Intl.ListFormat`).
- Link text says where it goes (e.g. „Wszystkie odbiory śmieci”); never a bare „Kliknij tutaj”. The timeline's „Szczegóły” is GOV.UK's summary-list action, with its visually hidden suffix („Szczegóły o odbiorze śmieci, wtorek, 10 listopada”), as GOV.UK's „Change”.

## Live blocks and loading placeholders

Every page is a static shell; what changes between imports is a live block, its own `<Suspense>` hole read per request (`LiveBlock`, `web/components/live-block.tsx`). Only the address pages have one; every other page is a static shell only. **The address pages and their subpages (`/smieci`, `/woda`, `/prad`, each with its `?nr=`) are one block each: one skeleton, one reveal.** The whole page body (h1, „Zmień adres”, the timeline, every section) sits behind one `<Suspense>` (`PlaceSuspense`, `web/components/place-suspense.tsx`) and comes in all at once, after the slowest block. Every block's data is read at once, after `io()`, in one `Promise.all` (`hubData` in `web/components/hub.tsx`, `subpageData` in `web/components/module-page.tsx`), so the wait is the slowest block, not the sum. Nothing date-dependent is ever prerendered: an address route's static shell holds only the layout and the skeleton, no date and no waste type.

The breadcrumbs are in the layout's `@breadcrumbs` slot, before `<main>`, so they cannot sit inside the page's own boundary without a root-layout boundary, which would keep the old page on screen during a navigation (a React transition never shows an already-revealed fallback). Instead the slot's fallback is the skeleton's first line (`CRUMBS_SKELETON`), and the trail reads the page's own data through React's `cache()` (one read per request, shared by the slot and the page), so both resolve on the same promise and come in together. The revealed content starts GOV.UK Frontend's components itself (`<GovukFrontend />` inside `PlaceSuspense`), as it always arrives after the layout's start: the waste subpage's button and the number error's summary (its focus).

- **Skeleton:** blank space as wide as some text, painted as a bar (`Skeleton`, `web/components/skeleton.tsx`), in the element and GOV.UK class it stands for, on GOV.UK's light grey (`.app-skeleton`, rounded as the bin markers), so it scales with text zoom. Blank, so no crawler or text-only reader finds words in it. The address pages' skeleton is **generic, not the page's shape**, so a new section needs no new skeleton: the page head's band (`.app-band`) with the h1's bar and „Zmień adres”'s, then one card (`.app-card`, the pages' own; a `govuk-heading-s` bar and two `govuk-body-s` bars, as a card's 16 px rows), one component for every address route. It is short, about as tall as the shortest address page (`/woda` with no cuts), and no `min-height` holds the page, so on a short page the footer barely moves at the reveal, and never up; on a long page it moves down, already below the first screen. A card's bars sit evenly inside it: 15 px top, bottom and left. The breadcrumbs' slot shows the skeleton's first line, the trail's bar. One „Sprawdzamy…” for all of it. The waste subpage keeps its own route folder (`web/app/adres/[id]/smieci/`); every subpage route shares one body (`SubpageRoute`, `web/components/subpage-route.tsx`).
- **Motion:** a skeleton is seen as soon as it renders, no delay and no fade in; CSS only, on `.app-skeleton` a subtle pulse (opacity only); the reveal through React's `<ViewTransition>` (on an address page the whole content and its breadcrumbs, once) as Next.js's "Suspense reveals": the skeleton fades out and the block fades in, opacity only, 150 ms each, at once, no slide; the page itself never crossfades (`::view-transition-*(root)` off), so a reload while scrolled does not jump and a navigation swaps at once (`web/app/site.scss`). The main content takes no scroll anchor (`overflow-anchor: none` on `#main-content`), so a reload restores the plain scroll offset, not Chromium's saved anchor, which can match the skeleton's box and land the page too high. Under `prefers-reduced-motion: reduce` no pulse and no reveal: the skeleton is still, and the block swaps at once. `::view-transition { pointer-events: none }`, so clicks during a reveal reach the page.
- **Screen readers:** the skeleton is `aria-hidden`; once per placeholder, „Sprawdzamy…” in `govuk-visually-hidden` (`LOADING`). No live region and no `aria-busy`: nothing is announced on load, and the fallback is replaced, not updated in place, so there is no element left to mark busy.
- **Freshness:** a block's check time comes from the same read as its data.
- **„Dziś”, „Jutro”, „Za 5 dni”:** in the HTML with the rest of the page, no skeleton of their own (`DayWord`, `web/components/day-word.tsx`): rendered for the Warsaw day of the per-request read (`place.today`, given by `WarsawToday`, a context provider, `web/components/warsaw-today.tsx`), then kept to the device's day: React hydrates with the server's day (`useSyncExternalStore`'s `getServerSnapshot`) and re-renders only if the device's differs; a page mounted in the browser (the router's cached payload) starts from the device's day; re-checked every minute, on `visibilitychange` and on `pageshow` (a tab left open past midnight, the back/forward cache). The waste dates from today on (`PickupSchedule`, `WasteStatus`) use the same day. The dates around the word are absolute, with their weekday.

The search lives only on the home page: its field is in the static shell, the same element before and after hydration (`web/components/address-search.tsx`). What „Szukaj” finds is drawn under the field, in a polite live region: one place opens its page; several are listed („Wyniki wyszukiwania”, h2, then „Dla „…” znaleźliśmy 3 adresy. Wybierz swój.” and the links); none is plain text, never an error („Nie znaleźliśmy „…””, h2, then what to try). While the index is still loading, `web/components/search-skeleton.tsx` (one result) holds the place. GOV.UK's error summary and field error only for an empty submit, never on load.

## Home-screen app

Opened from the home screen (`display-mode: standalone`), every page has a strip in the header's colour, 10 px deep, fixed at the top (`.govuk-template__body::before`, `web/app/site.scss`): Safari takes the status bar's colour from it, not from theme-color. It is the only own fixed element, sits on the header's own colour when the page is not scrolled, and is hidden while the skip link is focused. In a browser tab nothing changes. The status bar style is `default`, never `black-translucent` (`web/app/layout.tsx`).
